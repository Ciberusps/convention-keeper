# Интеграция с движковой валидацией ассетов (AssetValidation Base Rule)

**Статус:** реализовано (базовое правило + StateTree в плагине)  
**Связанные области:** Convention Keeper rules, `UEditorValidatorBase`, `UEditorValidatorSubsystem`, Data Validation (UE5), StateTree

**Классы:** в опциональном плагине **`ConventionKeeperValidation`** (модуль `ConventionKeeperValidationEditor`): `UConventionKeeperRule_AssetValidation`, `UConventionKeeperRule_StateTreeDeprecatedNodes`, `UConventionKeeperStateTreeDeprecatedNodesEditorValidator`. Там же в `ConventionKeeperValidation.uplugin` объявлены зависимости **ConventionKeeper**, **DataValidation**, **StateTree**. Базовый **`ConventionKeeper.uplugin`** не тянет другие плагины движка.

## Зачем отдельный Base Rule

Идея ввести **`UConventionKeeperRule`-наследника уровня «AssetValidation»** (рабочее имя), который **не придумывает свою семантику проверок**, а **подключается к штатной системе валидации Unreal Engine** для выбранных типов ассетов и сценариев.

**Пример из задачи:** для StateTree (Conditions / Tasks / Evaluators) запретить использование флага **Deprecated** на полях/узлах, т.к. это приводит к потере данных в редакторе и в релизных билдах.

### Насколько это хорошая идея

| Плюсы | Минусы / риски |
|--------|----------------|
| Один язык проверок с тем, что уже есть в движке (валидаторы, `IsDataValid`, Editor validators) | Дублирование с уже существующими Project Settings → Validation, если не договориться о границе ответственности |
| Сложные правила (графы, ссылки между объектами) ближе к «истине», чем чистый Asset Registry | Стоимость по CPU/RAM и времени при широком scope |
| Результаты можно унифицировать с Convention Keeper (Message Log, RuleId, доки) | Версии UE: API подсистем валидации меняется между минорными релизами — нужна абстракция |

**Вывод:** идея **здравая**, если Convention Keeper остаётся **оркестратором** (когда что запускать, какой scope, как репортить), а **сами проверки** живут в движке или в тонких `UObject`/`UAssetValidator`-подобных классах.

## Можно ли встроить в существующий Base Rule

Кратко по вариантам:

| Существующий rule | Подходит? | Почему |
|-------------------|-----------|--------|
| **FolderStructure** | Нет | Про иерархию папок и диск, не про загрузку UObject |
| **NamingConvention** | Нет | Имена путей/строк, не семантика ассета |
| **AssetNaming** | Слабо | Префиксы/суффиксы по типу из AR; не про внутренние флаги Deprecated |
| **AssetPlacement** | Слабо | Размещение по сегментам пути |

**Рекомендация:** отдельный rule с чётким контрактом. В коде это **`UConventionKeeperRule_AssetValidation`**: он вызывает **один** выбранный класс `UEditorValidatorBase` на каждый ассет в scope (не прогоняет все зарегистрированные валидаторы подсистемы — только указанный класс). Опция **`bRunClassIsDataValid`** при необходимости добавляет проход `UObject::IsDataValid` до валидатора (как в `UEditorValidatorSubsystem`).

## Реально ли построить на «дефолтной» системе UE

Да, в типичном UE5-проекте есть несколько пересекающихся механизмов (точные имена классов зависят от версии движка):

1. **Data Validation** на уровне `UObject` — переопределение валидации объекта и контекста результата (ошибки/ворнинги с привязкой к свойству).
2. **Editor Asset Validation** — подсистема редактора, которая может прогонять зарегистрированные валидаторы по ассетам/типам.
3. **Коммандлеты / сессии полной проверки** — то, что CI или «Validate All» могут дергать пакетно.

Базовый rule **AssetValidation** триггерит выбранный `UEditorValidatorBase` на scope. Для StateTree в плагине поставляются **`UConventionKeeperStateTreeDeprecatedNodesEditorValidator`** и preset-правило **`UConventionKeeperRule_StateTreeDeprecatedNodes`** (лимит типа `UStateTree`, валидатор задан по умолчанию). Дополнительные проверки по-прежнему можно задавать своим `UEditorValidatorBase` в проекте и указывать класс в **`EditorValidatorClass`**.

## Полная валидация проекта и память

### Что происходит по шагам

- **Только Asset Registry (без загрузки пакетов):** можно узнать пути, классы, зависимости на уровне метаданных. Этого **недостаточно** для проверки «Deprecated на внутренних полях» графа StateTree — нужен разобранный/загруженный объект (или хотя бы сериализация, что по сути близко к загрузке).
- **Валидация через загрузку пакетов:** для каждого релевантного `.uasset` движок **загружает пакет в память**, строит объекты, потом можно выгрузить/GC. Обычно это **не** «все ассеты одновременно в RAM», если реализация **последовательная/батчевая** с освобождением между пакетами.
- **Пик памяти** всё равно может быть заметным на больших Blueprint/StateTree/DA из-за размера пакета и графов.

### Итог по ресурсам

| Scope | Память | Время | Пригодность для «Deprecated StateTree» |
|-------|--------|-------|----------------------------------------|
| Один сохранённый пакет | Низкая | Низкая | Да |
| Папка / выбор в Content Browser | Средняя | Средняя | Да |
| Весь `/Game` | Высокая по длительности, пики умеренные при батчах | Высокая | Да, но только как явный «тяжёлый» режим |

## Нужны ли ограничения: только save vs full

Рекомендуемая модель **трёх уровней** (можно отразить в настройках плагина и в самом rule):

1. **On save / on asset change (узкий scope)**  
   - Запуск только для **текущего пакета** (как уже делается для части правил).  
   - Минимальная задержка, предсказуемая память.  
   - Подходит для правил уровня «не сохраняй с Deprecated».

2. **Интерактивный scoped (папка, мультивыбор, авто после создания папки — если расширить)**  
   - Явный лимит или предупреждение по числу ассетов (аналог уже существующего порога «large validation» в Convention Keeper).  
   - Батчи + опциональный progress/cancel.

3. **Full project / CI (commandlet)**  
   - Только с **подтверждением** в UI или отдельной командой для ночных прогонов.  
   - Документировать: длительность, отсутствие гарантии «всё в RAM сразу», но **гарантированная** полная проходка по выбранным типам.

**Для правила про Deprecated StateTree** логично:

- **обязательно** иметь смысл в режиме **save** (чтобы не закоммитить битые данные);
- **опционально** full scan как периодическая гигиена.

Отдельно: если команда хочет **вообще без загрузки** — для части кейсов возможны эвристики по **сырым тегам/метаданным** (редко достаточно для графов). Для StateTree надёжный путь — **загруженный объект + валидатор**.

## Предлагаемая архитектура фичи (высокий уровень)

```
UConventionKeeperRule_AssetValidation
  ├─ Scope: какие классы / пути / фильтр AR
  ├─ Mode: OnSave | ScopedSelection | FullWithConfirm | CommandletOnly
  └─ Backend: UEditorValidatorBase (Data Validation API)
        ├─ В плагине: UConventionKeeperStateTreeDeprecatedNodesEditorValidator
        └─ Опционально: проектные подклассы UEditorValidatorBase
```

- **Convention Keeper** = политика (когда, где, как репортить, RuleId, ссылки на Docs).
- **Unreal validation** = механика (что именно считается ошибкой).

## Критерии готовности фичи

- [x] Базовое правило `UConventionKeeperRule_AssetValidation` + эталонный валидатор StateTree в плагине.
- [ ] Поведение при **narrow scope** совпадает с ручным «Validate Asset» в редакторе (по смыслу, не обязательно по тексту сообщения).
- [ ] Full scan: порог предупреждения, батчи, отмена, логирование длительности.
